# 설계 결정 기록

형식: `날짜 · 결정 · 이유 · 버린 대안`

- 2026-10-27 · 열거형은 `StrEnum` 사용 · 오타를 모델 검증이 잡고, JSON 직렬화가 문자열 그대로임 · `Literal` (tier→가중치 매핑을 따로 둬야 함)
- 2026-10-27 · `category`는 고정 `StrEnum`(meal, sightseeing, shopping, cafe, transport, other) · 전략 프리셋이 카테고리로 분기하므로 철자 오류가 조용한 버그가 됨 · 자유 문자열
- 2026-10-27 · 모델은 `frozen=True` + `tuple` 사용 · 엔진 입력이 실행 중 바뀌면 결정론(2번 원칙)이 깨짐 · 가변 `list`
- 2026-10-27 · `ideal_duration`은 계산값, `Preference.value`는 제거(`Tier.weight`로 대체), 운영시간(`open_at`/`close_at`)은 `Activity`에 포함 · 중복 저장 시 불일치 위험, 엔진은 DB를 볼 수 없음 · 테이블 그대로 필드화
- 2026-10-28 · 이벤트는 타입별 모델 + discriminated union · 필수값 누락을 모델 검증이 잡고 `constraint_builder`가 타입이 보장된 값을 씀 · `params: dict` 단일 모델
- 2026-10-28 · `MUST_VISIT`는 일정에 없던 새 장소를 받고 `Op.ADD` 추가 · 사용자가 장소를 직접 지정하면 생성이 아니라 패치임 · 기존 일정 승격 해석
- 2026-10-28 · 장소 추천은 P2로 미룸(구현 시 엔진 바깥에서 후보를 뽑아 MUST_VISIT로 투입) · "일정을 생성하지 않는다"는 정체성과 11/1 엔진 마감 · MVP에 추천 포함
- 2026-10-28 · 이동시간을 `RecoveryInput.travel`(무방향 쌍, 호텔은 `"hotel"`)로 엔진에 직접 입력, 누락·중복은 모델이 거부 · 엔진은 DB를 볼 수 없는 순수 함수 · 엔진 내부에서 캐시 조회
- 2026-10-28 · `DelayEvent`는 `minutes`가 아니라 `start_time`(다시 움직일 수 있는 시각) · 기획서 시나리오 A가 "지금 출발해"(현재시각 입력)이고, "30분 늦어"는 서비스 계층에서 변환 가능 · 지연 분 단위 입력
- 2026-10-28 · 시나리오 테스트는 정확한 시각표가 아니라 기대 속성(위반 0, 꼭 4개 유지, 변경 목록이 모든 일정을 포함)을 검사 · 기획서 시각표는 "설명용 가정치"임 · 시각표 전체 일치 검사
- 2026-10-28 · LLM 제공자는 OpenAI(첫 구현), `llm/provider.py`로 추상화해 교체 가능하게 유지 · 사용자 선택 · Anthropic
- 2026-10-29 · 검증기는 시나리오 A 해결안(기획서 표)을 기준 통과 사례로 삼아, 규칙마다 "그 값만 바꾼" 테스트를 둠 · 위반이 정확히 그 규칙 하나에서만 나는지 확인하려고 · 규칙마다 별도 입력을 새로 작성
- 2026-10-29 · 검증기에 `coverage`(모든 일정이 변경 목록에 정확히 한 번씩)와 `past`(바뀐 일정은 "지금" 이후에 시작) 규칙 추가 · 일정을 목록에서 빼면 must 삭제 검사를 우회하고, 지연 이벤트를 무시한 후보도 통과함 · 두 규칙 없이 6개만 검사
- 2026-10-29 · `past`는 시작 시각이 바뀐 일정만 검사 · 진행 중인 일정을 연장하는 경우(시나리오 E)를 위반으로 오판하지 않으려고 · 모든 변경 일정 검사
- 2026-11-01 · 현재 위치를 이벤트의 `location_id`(이동시간 표의 노드 id, 기본 `"hotel"`)로 받고, 검증기에 `origin` 규칙(앞으로 남은 첫 일정은 현재 위치에서 도달 가능) 추가 · 이벤트 시점에 어디 있는지 모르면 첫 일정의 도달 가능성을 검사할 수 없음 · 좌표로 현재 위치 입력(표에 없는 점은 이동시간 계산 불가)
- 2026-11-01 · RcBreakdown은 가중치를 곱하기 전 D 값을 저장하고 rc_total에서만 가중 · 보존율이 D_drop+D_shrink+D_sub 원값을 쓰므로 · 가중 기여도 저장
- 2026-11-01 · D_move 단위는 시간(D_time과 동일), 음수 허용(클램프 안 함) · 분 단위면 삭제로 줄어든 이동이 삭제 비용만큼의 보상이 됨 · 분 단위, 0으로 클램프
- 2026-11-01 · cost 계산은 변경 목록을 activity_id 순으로 정렬한 뒤 합산 · 소수 덧셈은 순서 의존이라 입력 순서만 달라도 마지막 자리가 달라짐(테스트로 발견) · 입력 순서 그대로 합산
- 2026-11-01 · 기본 가중치에서 시나리오 A의 기획서 해결안(오모테산도 삭제)이 최적이 아님: RC 기획서안 2.312, 전부 유지·단축안 1.425, 삭제+쇼핑·카페만 단축안 1.588 · (결정됨, 아래 항목 참고)
- 2026-11-01 · 시나리오 A 기대값에서 "오모테산도 삭제"를 제거하고 "위반 0, 꼭 4개 유지"만 검사 · DP 결과(삭제 0, RC 1.188, 보존율 95.2%)가 기획서 해결안(RC 2.312, 89.2%)보다 비용과 보존율 모두 좋음 · 정답에 맞춰 가중치(w_shrink↑/w_drop↓)를 조정하는 안
- 2026-11-01 · 버퍼(이동시간 외 추가 여유)는 전략의 하드 제약(`Strategy.min_buffer`)이고 기본 0, "여유 보존"만 20분 · 기획서의 시나리오 A 해결안이 버퍼 0 구조라 기본을 0으로 둠 · 기본 10분(전 테스트·시나리오 재작성 필요). 하루 활동시간 상한은 값이 없어 보류
- 2026-11-01 · EXTEND 이벤트는 비용이 아니라 하드 제약(연장 길이 정확히 충족)이며 검증기가 `event` 규칙으로 확인 · 사용자가 명시한 요청이므로 · 연장을 선호(소프트)로 처리
- 2026-11-01 · `location_id`가 일정 id이면 그 일정은 진행 중으로 보고 시작 시각을 고정(`in_progress` 규칙) · 이미 시작한 일정의 시작을 바꿀 수 없음 · 진행 중 개념 없이 모든 일정을 지금부터 새로 배치
- 2026-11-01 · 시나리오 E 기대값에서 "오모테산도 단축, 점심 이후 불변"을 제거하고 위반 0·꼭 유지·연장 충족만 검사 · 기본 가중치에서 엔진은 점심 이후를 30분 늦추고 쇼핑을 줄이는 해(RC 0.154)를 택함. w_time(0.05/시간)이 작아 시각 이동이 거의 공짜임 · 정답에 맞춘 가중치 조정. 가중치는 50개 비교 실험에서 한꺼번에 조정(미결)
- 2026-11-01 · (한계) 현재 위치는 이동시간 표의 노드(호텔 또는 남은 일정 id)만 가능 · 끝낸 일정 위치나 임의 좌표는 표현 불가 · 좌표 기반 추정 이동시간 삽입은 후속 과제
- 2026-11-02 · `Activity.outdoor`를 참/거짓/모름(None) 3상태로, 모름인 일정은 비 시간대에도 막지 않고 결과에 `needs_check`를 표시 · 우천 시 운영 여부 데이터가 없는데 임의로 정하면 8번 원칙 위반 · 모름을 옥외/실내 중 하나로 가정
- 2026-11-02 · 이벤트→제약 변환은 `constraint_builder.py`(DP가 사용)로 모으고, 검증기는 이 파일을 쓰지 않고 이벤트를 직접 읽음 · 변환 규칙에 실수가 있어도 검증기가 같은 실수를 공유하지 않게 함 · 검증기가 constraint_builder 재사용
- 2026-11-02 · 시나리오 B 기대값에서 "오모테산도만 변경"을 제거하고 "삭제 없음·오모테산도만 단축·스카이 needs_check" 검사 · 엔진은 하라주쿠를 5분 앞당겨 오모테산도를 25분 확보(w_time이 작아 시각 이동이 거의 공짜: A, E와 같은 현상). 이동량 직접 페널티 여부는 50개 실험에서 결정(미결) · 정답에 맞춘 가중치 조정
- 2026-11-02 · 체력(FATIGUE) 최소 버전: 일정에 `walking`(참/거짓/모름)을 두고, 걷는 활동은 원래 길이의 `walking_ratio`(기본 0.5, 5분 올림, 최소 체류 이상)까지만 허용(하드 제약) · 기획서 D의 핵심("체력에 맞춰 쇼핑을 줄인다")을 데이터 추가 최소로 표현. 모르는 일정은 막지 않고 needs_check · 택시 이동(이동시간 표 교체)과 도보 구간 제한, 카페 연장은 후순위
- 2026-11-02 · `FatigueEvent.max_walk_minutes`를 `walking_ratio`로 교체 · 도보 구간 제한은 택시 이동을 만들 때 다시 도입하며, 쓰이지 않는 필드를 남기면 오해를 부름 · 쓰지 않는 필드를 유지
