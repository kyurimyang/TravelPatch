# TravelPatch 점검 결과 (2026-11-19)

모바일 375px에서 실제로 등록 → 구멍 알림 → 패치 → 박음질까지 써 보고, 백엔드 pytest·ruff·black, 프론트 build·lint를 돌린 결과.
CLAUDE.md 14·15절대로 진행할 것: 설계 결정이 필요한 항목은 대안 2–3개 + 추천만 제시하고 사용자 결정 후 구현. 엔진·스키마·불변식 변경은 구현 전 확인.

## A. 기능 — 우선순위 높음

### A1. 이미 다녀온 일정이 "삭제"로 계산됨 (설계 결정 필요)
- 재현: 오늘 일정 등록(09:00 센소지 … 11:50 우에노 …) → 12:08에 구멍 알림 "수선하기" → 센소지가 `삭제 · 오늘은 빼요`, 이유 "원래 시각이 이미 지나서", "되살리면 어떻게 되나요?"까지 뜸. 보존율 73%로 떨어짐.
- 원인: `frontend/src/lib/recovery.ts` `planRequestFor`가 `dropped`만 빼고 지난 항목도 그대로 보냄. 엔진 `validator._check_past`는 "지금 이전 항목 = 놓친 것"으로 봄. 보존율 분모(Σ value)에도 지난 항목이 들어감.
- 시나리오 A–E·eval50은 모두 아침에 시작해 이 경우가 테스트되지 않음 → 회귀 시나리오 추가 필요(하루 중간 복구).
- 결정할 것: 지난 일정을 어디서 거를지(프론트/서비스 계층/엔진 입력에 status), "끝났나요?"를 물을지 시각으로 추정할지, 보존율 분모에서 뺄지.

### A2. 구멍 알림 지연이 두 번 더해짐
- 재현: 11:50 우에노, 지금 12:08 → 알림 "18분쯤 늦어지고 있어요" 프리셋 → 해석 칩 "12:26부터 움직일 수 있어요". 18분이 이미 지난 시각(now) 위에 한 번 더 더해짐.
- 같이: Recover의 "다음 조각"이 알림 대상(우에노)이 아니라 13:00 점심(`planned_start >= nowMin`), "있는 곳" 기본값이 숙소.
- 관련: `components/HoleAlert.tsx` preset, `pages/Recover.tsx` 145행 `next`, 142행 `where`.

### A3. 식사가 비상식적인 시각으로 이동 + diff 목록 순서
- 재현(A2 이어서): 점심 13:00 → 16:55–17:55(15:00 스카이 예약 뒤). 위반 0이지만 사람 눈엔 이상함.
- diff 목록이 원래 순서로 정렬돼 13:20 → 16:55 → 15:00으로 시간이 뒤섞여 보임.
- 결정할 것: 식사 시간대 제약(time_window) 도입 여부·범위. 목록 정렬 기준(새 시각 vs 원래 순서+표시).

### A4. "왜?" 이유·고정 버튼 불일치
- 예시 여행 + "출발이 늦어졌어요"(08:50, 2시간 지연): 메이지 신궁 이유 "원래 시각이 이미 지나서" — 실제 이유는 "10:50까지 못 움직여서"(DELAY의 start_time). `lib/reasons.ts` FORCED.past 문구가 DELAY에선 틀림.
- 같은 항목에 "이건 원래대로 둘래요(고정)" 노출 → 누르면 항상 실패. forced_by에 past가 있으면 숨기거나 비활성화.
- 지난 항목 삭제에 "되살리면?" 노출(A1과 같이 처리).
- 조사 하드코딩 "을(를)": `pages/DiffView.tsx` 146·156·164행 ("메이지 신궁을(를)"). 받침 판별 유틸로.

### A5. 일정 확인(Confirm) 화면
- 끝 시각 짐작(90분) 때문에 다음 일정과 겹친다는 경고가 뜨는데 그날 탭은 "확인 끝". 짐작 끝 시각을 다음 시작 − 이동 정도로 자르거나, 경고가 있으면 "확인 필요"로.
- 상호 없는 일반 일정("이자카야 저녁")도 가부키초의 아무 가게로 자동 확정됨 → 휴무 판정·대체 추천이 그 가게 기준이 됨. "장소 미정" 허용 여부 결정 필요.
- 이치란이 그날 동선(아사쿠사·우에노)과 무관하게 숙소 근처 신주쿠점으로 잡힘(숙소 기준 locationBias). 앞뒤 일정 좌표 기준 bias 검토.
- 장소 검색이 날짜 탭을 눌러야 시작됨(DAY 2를 눌러야 검색). 긴 여행이면 탭을 다 눌러야 함.

### A6. 화면 이동 시 스크롤 위치 유지 버그
- Confirm·Grade·Main·박음질 완료 화면이 이전 화면 스크롤 위치(중간·아래)에서 열림. `scrollTo`/`ScrollRestoration` 코드 없음.

### A7. 테스트·빌드
- pytest 324 중 1 실패: `tests/api/test_disruptions.py::test_empty_text_is_rejected_by_validation` — OpenAI 키 없으면 빈 입력에 422 대신 503(`get_provider` 의존성이 본문 검증보다 먼저 실패). 키 없는 환경(CI)에서 깨짐.
- black(기본 88자)과 ruff(line-length 100) 설정 불일치 → black이 70개 파일을 바꾸려 함. `[tool.black] line-length = 100` 추가.
- 프론트 `fetch`에 타임아웃 없음 → 네트워크가 느리면 "읽는 중…"이 끝나지 않을 수 있음(AbortController).
- 번들: `src/assets/wordmark.png` 468KB(1200×408) → WebP/SVG. CSS 536KB(대부분 폰트 @font-face 460개).
- `index.html`: `<title>frontend</title>`, `lang="en"`, OG·description·theme-color 없음. favicon 확인.
- `AppFrame.css` `min-height: 100vh` → 모바일 주소창 때문에 `100dvh` 권장. 스크롤 시 프레임 배경이 하단 고정 버튼보다 먼저 끝나는 현상.

## C. 문구·서체 개편 (2026-11-19 사용자 결정)

### 결정
- **브랜드 = 수선(패치워크) 세계관 유지.** 틀어진 일정을 새 원단(패치)으로 딱 맞게, 혹은 더 예쁘게 수선한다. 은유를 걷어내지 않는다.
- AI 티의 원인은 은유가 아니라 말투: 은유를 풀어 설명하는 문장, "~해 드려요/드릴게요", 모든 제목 밑 부제, 반복되는 안심 문구. → 은유는 설명 없이 그냥 쓰고, 짧게.
- 제목 서체 고운바탕 → Pretendard(굵기·크기·자간으로 위계). 손글씨(Gaegu)는 태그·완료 축하 같은 "손으로 쓴" 자리에 그대로.

### 브랜드 단어 (이 다섯 개만)
| 단어 | 뜻 | 쓰는 곳 |
|---|---|---|
| 원단 | 원래 일정(하루 한 장) | 메인, 여행 원단 탭 |
| 구멍 | 틀어진 자리 | 구멍 알림, 상황 입력 |
| 패치 | 구멍에 대는 새 조각 = 변경안 | 후보, 결과 |
| 수선 / 꿰매기 | 고치는 일 / 확정 | 버튼 |
| 패치워크 | 여행이 끝난 뒤 완성된 기록 | 패치 모음 |

- 동작 순서 = 실제 수선 순서: **대 보기(확정 전) → 꿰매기(확정) → 뜯기(되돌리기)**.
- 은퇴: 재단, 시침질, 박음질, 실 풀기, 풀린 실. (로딩 문구의 "실 꿰는 중…" 같은 소리 효과는 유지)
- "더 예쁘게": 연장(extend)이 들어간 패치일 때만 완료 문구를 "원래보다 여유 있게 수선했어요"로. 데이터가 있을 때만(불변식 8).

- 타입 스케일 토큰 추가 후 적용(하드코딩 11px 포함 정리), 제안값:

## D. 원단 지도 개편 (2026-11-19 사용자 결정: 2안)

### 지금 문제
- `pages/Main.tsx`의 `SLOTS`가 시안에서 옮긴 고정 칸 4개 + 고정 원단 4종 → 모든 날이 같은 모양.
- `slice(0, SLOTS.length)` 때문에 5번째 일정부터 지도에서 빠짐(19:00 이자카야 누락).
- 칸 크기가 고정이라 라벨이 잘림("11:50 우에노 …").

### 결정
1. **조각 크기 = 머무는 시간**(end − start). 개수 제한 없이 그날 일정으로 레이아웃을 만든다(flex-wrap 비율 또는 행 단위 배치). 라벨은 시각 + 짧은 이름, 잘리면 시각만.
2. **무늬 = 카테고리 계열, 색 조합 = 날짜.**
   - 계열 5개 × 무늬 4종 = 20종
     - 관광: 잔꽃 · 물방울 · 도트 · 꽃송이
     - 식사: 깅엄 · 타탄 · 윈도페인 · 와플
     - 쇼핑: 세로줄 · 사선줄 · 티킹 · 셰브론
     - 카페: 퀼팅 · 코듀로이 · 니트 · 아가일
     - 기타·이동: 리넨 · 데님 · 헤링본 · 와이드줄
   - 색 조합 12개(바탕/무늬/밝은 실): 머스터드, 버터, 네이비, 올리브, 러스트, 인디고, 세이지, 테라코타, 로즈, 버건디, 스카이, 탄. 기존 tokens의 --tp-* 색에서 출발.
3. **날마다 다르게, 같은 날은 항상 같게.** 여행 id + 날짜로 만든 해시(시드)로 그날의 색 조합과 계열 안 무늬를 고른다(Math.random 금지 → 새로고침해도 같음). 규칙: 바로 전날과 색 조합이 같으면 다음 것으로 넘긴다. 장거리(30일+)도 반복이 눈에 띄지 않음.
4. **패치 표시.** 패치가 붙은 조각(patched/substituted)은 위에 작은 패치(박음질 테두리, 살짝 회전)를 덧대고, 뺀 조각(dropped)은 흐리게.

### 구현 메모
- `styles/patterns.css`: 무늬 20종을 **색을 변수로 받는 형태**로 정의.
  예: `.fab-gingham { background: repeating-linear-gradient(0deg, color-mix(in srgb, var(--fab-light) 40%, transparent) 0 6px, transparent 6px 12px), …, var(--fab-base); }`
  색 조합 12개는 `--cw-mustard-base/accent/light` 같은 토큰으로 tokens.css에. → 20 + 12 정의로 240 조합.
- `lib/fabric.ts`(신규): `fabricFor(tripId, date, category, index) → { patternClass, colorway }` 순수 함수 + 단위 테스트(같은 입력 같은 출력, 전날과 색 조합이 다름).
- Main의 원단 지도, Patchwork의 패치워크(조각마다 원단)도 같은 함수를 써서 메인과 패치 모음의 같은 날 원단이 일치하게.
- 장식용 지도라 실제 위치가 아님(기존 주석 유지). 375px에서 일정 2개·5개·9개인 날 각각 확인.
